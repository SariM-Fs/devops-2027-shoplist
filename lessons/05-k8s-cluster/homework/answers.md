# שיעור 5 — שיעורי בית

## חלק א — מפת ה-cluster

| רכיב | איפה הוא רץ (הנהלה / כל node) | מה הוא עושה, במשפט אחד | אנלוגיה |
|---|---|---|---|
| API server | הנהלה | הרכיב שדרכו מתקשרים עם Kubernetes, כל בקשה עוברת דרכו | הדלפק בכניסה, כל הזמנה עוברת דרכו |
| etcd | הנהלה | הזיכרון שבו נשמר המידע על מצב ה-cluster | פנקס ההזמנות הגדול |
| scheduler | הנהלה | מחליט על איזה node ירוץ כל pod חדש | מנהלת המשמרת שמחליטה באיזה מטבח יאפו כל עוגה |
| controller manager | הנהלה | דואג שהמצב בפועל יתאים למצב הרצוי | המפקחת שבודקת את הוויטרינה מול הפנקס ומזמינה עוד עוגה כשחסר |
| kubelet | כל node | אחראי על ניהול ה-pods ב-node שלו ומדווח להנהלה | ראש הצוות של המטבח |
| container runtime | כל node | מריץ את ה-containers בפועל | התנור, שהופך את המתכון לעוגה |
| kube-proxy | כל node | מנתב תעבורה מ-Service אל ה-pods המתאימים | המלצר שיודע מאיזו עמדה להביא את העוגה |
| coredns | pods בתוך ה-cluster (ב-kube-system) | מתרגם שמות של Services לכתובות IP | ספר הטלפונים הפנימי, מחפשים לפי שם |

## חלק ב — תרחישים

### 1. scale
 כשאני מריצה את הפקודה להגדיל את מספר ה-Pods מ-2 ל-4, ה-Deployment מעדכן את ה-ReplicaSet, וה-ReplicaSet מזהה שחסרים 2 Pods ודואג ליצור אותם. אם בהמשך אחד ה-Pods נופל, ה-ReplicaSet מזהה שחסר Pod ודואג ליצור חדש, כדי שתמיד יהיו 4 Pods כפי שהגדרנו.
### 2. שלוש בלילה
-container runtime רואה שתהליך הסתיים. ה-kubelet שעל אותו node שם לב שה-container מת, הוא מבקש מה-container runtime להפעיל אותו שוב מחדש, ואז הוא עולה שוב בתוך אותו pod עם אותו שם ועל אותו node, רק מונה פעולות חדש עולה באחד.
 מקרה שני:
כמו המקרה הקודם רק הבדל משמעותי: עולה pod חדש עם שם חדש
### 3. node נכבה
 מקרה א:
אחרי כמה דקות כל ה-pods חוזרים לרוץ, רק על nodes אחרים. המשתמשים כמעט לא מרגישים, כי בינתיים ה-pods שעל ה-nodes הבריאים ממשיכים לענות.
מקרה ב:
הכל פשוט נעצר, והאתר לא זמין.
### 4. מהכיתה לענן
 מקרה א:
ה-pods לא יעלו, והסטטוס יהיה ErrImageNeverPull, כי ה-nodes הם שרתים של אמזון, איפשהו בענן. הם לא רואים את המחשב שלי, ואין עליהם את ה-image. צריך להעלות את ה-image ל-registry, ולשנות את שורת ה-image לכתובת המלאה ב-registry.
מקרה ב:
NodePort לא מתאים לענן, כי אין localhost והכתובת של ה-node יכולה להשתנות. צריך לשנות את ה-type ל-LoadBalancer, ואז מתקבלת כתובת ציבורית קבועה.
### 5. pod בודד
 ה-pod של stats נוצר עם kubectl run, ולכן הוא pod בודד שאף אחד לא משגיח עליו. כשמוחקים אותו, הוא פשוט נעלם. ה-pod של web שייך ל-Deployment, וה-controller manager רואה שחסר pod ויוצר חדש. כדי ש-stats יחזור תמיד, צריך ליצור לו Deployment.
